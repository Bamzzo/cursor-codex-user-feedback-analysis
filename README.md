# Cursor / Codex 用户反馈分析

本项目以 Cursor、OpenAI Codex 等 AI 编程智能体为研究对象，基于公开社区中的真实用户反馈，分析用户主要关注什么、不同问题如何组合、反馈进入社区或 Issue 系统后如何被处理，以及论坛和 GitHub Issues 之间有哪些结构差异。

项目的核心思路不是简单地“抓数据、跑模型、画图”，而是把数据分析流程与业务问题连接起来：先确认数据能否支持研究，再根据不同问题选择主题模型、关联规则、生存分析和文本分类等方法，最后把统计结果转化为产品、研发和运营可以理解的判断。

## 一、研究框架

项目围绕五个相互衔接的问题展开：

1. **RQ1：用户在讨论什么？** 使用 Cursor 论坛正文，识别用户讨论的主要主题，并观察不同主题与版块、浏览、回复和采纳行为的关系。
2. **RQ2：问题如何组合出现？** 使用 Codex GitHub Issues 的多标签记录，分析标签共现、关联强度和时间稳定性，为问题分流和标签治理提供依据。
3. **RQ3：反馈如何被处理？** 使用 Issue 的创建时间、回复记录、关闭状态和关闭原因，分析首次回复、维护者回复、关闭和长期积压等过程。
4. **RQ4：论坛和 Issues 有什么差异？** 在统一时间窗口和统一文本规则下比较两个渠道的问题类型、产品入口、互动情况和可比性边界。
5. **扩展：文本能否辅助早期分流和处理判断？** 使用独立的 `issue_ml/` 模块验证文本是否能辅助区分 Bug 与 Enhancement，并探索早期信息对 Issue 完成结果的预测能力。

## 二、数据来源与分析单位

项目使用的主要数据来自公开接口和公开页面：

- [Cursor Forum](https://forum.cursor.com)：主题元数据、主题正文、帖子和互动信息；
- [OpenAI Codex GitHub Issues](https://github.com/openai/codex/issues)：Issue、标签、状态和创建/关闭信息；
- GitHub Issue 评论接口：评论内容、作者关联和回复时间；
- [Hacker News Algolia API](https://hn.algolia.com/api)：作为外部辅助对照，不承担核心结论。

不同数据源的分析单位不同：论坛主要以“主题”和“正文主题”为单位，GitHub 主要以“Issue”和“评论”为单位，Hacker News 以帖子为单位。因此，项目不把所有记录简单相加为一个“总样本”，每个比例都保留自己的分母和口径。

当前整理版使用的规模包括：约 4.1 万个论坛主题元数据、4,307 个进入主主题模型的有效正文主题、2.7 万条 Codex Issues、11.5 万条评论，以及约 8 万条 Hacker News 辅助数据。论坛正文覆盖并非全量，GitHub 标签也只是维护者标注，不能直接解释为全部用户的真实故障率。

## 三、从原始数据到图表的完整流程

### 1. 数据获取与质量核验

数据采集先探查总量、时间范围和分页边界，再按接口分页或时间切片抓取，最后将原始 JSON/JSONL 文件落盘。论坛数据通过 Discourse 的公开接口获取，GitHub 数据通过 Issue、评论和 Search 等接口交叉核对，Hacker News 通过 Algolia 接口按时间窗口获取。

采集完成后不直接进入建模，而是进行独立核验：论坛版块计数与实抓主题数核对；GitHub Issue 列表、Search API 和主键唯一性核对；评论关联情况核对；主数据文件的条数、字节数和 SHA-256 哈希在运行时重新计算；数据范围、时间截点、字段定义和异常记录写入审计结果。

这一阶段对应 `src/01_build_base.py`，主要结果写入 `outputs/integrated/`，派生数据写入本地 `data/derived/`。

### 2. 数据清洗与统一字段

公共数据底座完成去重、字段类型转换、时间标准化、文本清洗、评论关联和统一分类。论坛正文会去除 HTML、代码块、模板化页脚和过短文本；Issue 会统一标题、正文、标签、状态、关闭原因和时间字段；评论会关联到对应 Issue，并计算首次外部回复、维护者回复等时间指标。

项目同时建立统一分类字典和口径登记表，明确区分“官方版块”“NMF 主题”“Issue 标签”和“标题规则分类”，避免把平台自带分类误当作模型分类。清洗后的字段用于后续主题模型、关联规则、生存分析和跨渠道比较。

### 3. 探索性分析与基础审计

正式建模前，项目先检查样本量、缺失值、重复记录、时间分布、状态分布、标签覆盖率和评论关联率，并据此确定分母、时间窗口和可比字段。

同时区分几个关键概念：`closed` 表示 Issue 被关闭，不等于问题已经修复；`completed` 是维护者记录的状态，不等于用户满意；未关闭 Issue 是右删失样本；论坛正文覆盖有限，正文主题比例不能直接外推全部论坛主题。

### 4. RQ1：主题模型与用户讨论结构

RQ1 使用清洗后的论坛正文作为语料：先分词、去停用词并进行 TF-IDF 向量化，再使用 NMF 分解为 8 个可解释主题；随后根据高频词和代表性帖子命名，统计主题在版块、月份和互动指标上的分布，并通过近期普查语料重跑、bootstrap 和主题词匹配检查稳定性。

主要图表包括：`rq1_01_主题结构.png`（主题份额）、`rq1_02_主题与版块.png`（主题与官方版块）、`rq1_03_主题与互动.png`（主题与互动）、`rq1_04_覆盖与敏感性.png`（覆盖和敏感性）、`rq1_05`—`rq1_06`（近期语料扩展）、`rq1_07`—`rq1_10`（长期版块、互动和痛点扩展）、`rq1_11_k选择诊断.png`（主题数诊断）。

主结果显示，MCP/网络、IDE 界面、云端协作和模型路由是较突出的讨论方向，四类主题合计约占有效正文主题的七成。但主题是文本结构，不是用户需求强度，也不能把主题份额直接解释为产品故障率。

### 5. RQ2：标签共现与关联规则

RQ2 把每条多标签 Issue 看作一个事务，使用 Apriori 挖掘频繁项集和关联规则，并综合支持度、置信度、提升度、覆盖率、样本数、季度稳定性和时间外检验判断规则是否值得使用。

主要图表包括：`rq2_01_标签频率.png`、`rq2_02_共现热力图.png`、`rq2_03_支持度与提升度.png`、`rq2_04_季度稳定性.png`。结果显示 Windows/桌面端、CLI/TUI、沙箱权限、远程和云端等问题模块存在较稳定的组合关系，可用于首轮分流、标签补全和标签体系质检，但不直接证明因果关系。

### 6. RQ3：反馈处理过程与生命周期

RQ3 将 Issue 的处理过程拆成首次外部回复、维护者回复、关闭和长期积压等时间问题。项目使用 Kaplan–Meier 生存分析处理未关闭的右删失样本，并用 Aalen–Johansen 竞争风险模型区分 `completed`、`duplicate`、`not_planned` 等关闭结局。

预测扩展包含 30 天内关闭、3 天内首次回复和 90 天以上长期未关闭三个时间外任务。训练和测试按创建时间切分，并在两部分之间设置与预测窗口等长的 Purge Gap，减少未来信息泄漏。

主要图表包括：`rq3_01_处理过程.png`、`rq3_02_生存曲线.png`、`rq3_03_月度队列.png`、`rq3_04_模型ROC.png`、`rq3_05_竞争风险.png`，以及回复时长和预测校准诊断图。

主结论是快速关闭与长期积压并存。已关闭样本的条件中位时长约为 2.01 天，但纳入右删失后，整体生存中位关闭时间约为 127.8 天；30 天内 `completed` 的竞争风险约为 18.7%。因此不能只用关闭数量评价研发处理质量。

### 7. RQ4：论坛与 GitHub Issues 的跨渠道比较

RQ4 统一时间窗口、文本输入和标题规则，比较两个渠道的问题类型、产品入口、月份趋势和互动表现。由于版块、标签和状态定义不同，不能直接一一对应。入口和问题类型保留 `unknown`，并同时报告识别覆盖率；覆盖率不平衡时，已识别子集内的比例只能作条件描述，不能外推总体入口偏好。

主要图表包括：`rq4_01_问题类型.png`、`rq4_02_入口.png`、`rq4_03_月度趋势.png`、`rq4_04_可比性.png`。这部分的重点是说明两个渠道处于不同反馈漏斗：论坛更接近公开讨论和求助，Issues 更接近结构化问题提交和维护流程。

### 8. Issue ML 扩展：文本分流与完成结果预测

`issue_ml/` 承接 RQ2 和 RQ3：任务 A 对标题和正文做统一清洗，使用 TF-IDF 与逻辑回归进行 Bug/Enhancement 分类；任务 B 使用 Issue 创建时可见的结构特征和早期互动特征，以随机森林探索 7 天或 30 天内进入 `completed` 的可能性。扩展结果表明，文本适合辅助首轮类型分流，但处理周期和完成结果的预测信号有限，不能用于自动承诺处理时间或替代人工判断。

## 五、运行方式

公开仓库不包含完整原始数据集。若要重跑主流程，请准备公开数据文件并放入 `data/raw/`，或通过环境变量 `FEEDBACK_RAW_DIR` 指定数据目录，再按照 `docs/复现说明.md` 配置 Python 环境。

```bash
python src/run_all.py
```

也可以只重跑部分阶段：

```bash
python src/run_all.py --from 02 --to 05
```

运行后会更新 `data/derived/`、`figures/`、`outputs/` 和 `outputs/logs/`。如果缺少可选扩展所需的数据或材料，一键流程会跳过对应阶段，并在 `outputs/run_manifest.json` 中记录原因。

## 六、主要结果与业务含义

- **用户需求层面**：MCP/网络、IDE 界面、云端协作和模型路由是突出讨论方向，可作为产品问题池和用户研究访谈的候选主题。
- **问题治理层面**：标签组合体现入口、能力和运行环境之间的关系，可用于 Issue 首轮分流、标签补全和规则质检。
- **研发处理层面**：快速关闭和长期积压同时存在，应将完成、重复、不计划处理和仍未关闭分别跟踪。
- **渠道运营层面**：论坛和 Issues 是不同反馈入口，跨渠道比较需要保留 unknown 和覆盖率，不能简单合并。
- **自动化层面**：文本分类可以减少首轮整理成本，但弱预测结果不适合直接驱动排期、SLA 或自动处置。

## 七、研究边界

- 论坛正文覆盖率有限且早期存在分层抽样，正文主题份额不能外推全部论坛用户；
- 评论存在无法关联到当前 Issue 的记录，因此“无回复”比例可能被高估；
- GitHub 标签是维护者标注行为，不等于真实故障率或用户需求优先级；
- `closed` 不等于 `fixed`，`completed` 也不等于用户满意；
- 生存分析的观察终点来自数据快照，无法完全恢复历史上的重开过程；
- 主题模型和关联规则用于发现结构和线索，不直接证明因果关系；
- 文本预测只适合作为辅助信息，不能替代研发、产品和人工审核。

项目结果、图表和报告已保留在仓库中，原始数据未随仓库公开，因此外部使用者可以直接查看研究产出，但要完整重跑流程仍需自行准备相应数据。
