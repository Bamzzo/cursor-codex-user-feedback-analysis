# 项目整体讲解（全程版）

> 对象：AI 编程智能体的多源用户反馈与产品问题挖掘
> 数据快照：2026-09-13T02:20:37Z（由 Issue 最新时间字段推定，非已核实的抓取完成时间）
> 本文按课程两条主线（思维四部曲 / 建模六部曲）串讲，每一步回答：在做什么 → 为了得到什么 → 用什么方法 → 结果是什么 → 能推出什么 / 不能推出什么。

## 0. 一句话定位

用三份公开数据（Cursor 论坛、GitHub 上的 Codex Issues、Hacker News 少量对照），回答四个问题：**用户在说什么、问题怎么组合、反馈有没有被处理、两个渠道差在哪**；并把"这些数字到底能说到哪一步"写成结论的一部分。

技术难度不高。真正的难点全在**分母**上——五份数据有五个分母，任何一个百分比说错了分母，结论就整体失真。

| RQ | 问题 | 部曲性质 | 六部曲环节 |
|---|---|---|---|

**预测这一格我们做了，但结论是"做不好"——这也是结论的一部分，不是失败。**

## 2. 第一部分 · 数据（描述性的前提）

### 2.1 先拆问题：业务问题 → 可算问题

| 业务问题 | 翻译成可算的问题 | 会踩的坑 |
|---|---|---|
| 用户在抱怨什么 | 正文 → TF-IDF → NMF 主题份额 | 份额是"帖子占比"，不是"痛感强度" |
| 问题之间什么关系 | Issue 标签 → 频繁项集 → 关联规则 | 标签是维护者打的，反映分流习惯 |
| 官方响应快不快 | 首次回复 / 30 天关闭 / 生存曲线 | closed ≠ fixed；删失不能当 0 天 |
| 论坛和 GitHub 差别 | 两渠道统一标题规则 → 类型分布 | 版块 vs 标签，比的不是用户 |

这一步不是形式主义。第一行和第二行的坑，直接决定了后面能不能说"某类问题最严重"。

### 2.2 五个数据源，五个分母

| 数据 | 原始记录 | 可用分母 | 在本项目中的角色 |
|---|---:|---:|---|
| Cursor 论坛主题元数据 | 41,218 | 41,218 | 版块、互动、月度结构 |
| Cursor 论坛正文 | 4,322 主题 / 18,498 帖 | **4,307**（清洗后） | RQ1 主题建模，仅正文子集 |
| Codex Issues | 27,756 | 27,320 有标签 / **25,519 多标签** | RQ2、RQ3、RQ4 |
| Codex 评论 | 115,280 | 97,034 可关联 / 96,999 进入计算 | 首次回复、维护者回复 |
| Hacker News | 80,510 | 16,506 关键词命中 | 仅辅助对照，不承担核心结论 |

**没有"一个总样本"。** 论坛主题与帖子是包含关系，Issue 与评论是两个分析单位，混加成"28 万条数据"是错的。报告里每一个比例都带自己的分母。

最要紧的一条：**论坛正文只覆盖 10.5%（4,322/41,218）**，且 2026-07 前主要是分层抽样（388 个主题），之后才是全量普查（3,934 个）。所以 RQ1 的所有份额，只对"有正文的 4,307 条"负责，不能外推到 2023—2026 全历史。

### 2.3 预处理四步：具体做了什么

| 课件四步 | 本项目动作 | 可核对的结果 |
|---|---|---|
| 清洗 | 去 HTML、代码块、诊断页脚、Discourse 缺陷模板页脚；剔除过短正文 | 4,322 → 4,307 个可用主题 |
| 集成 | 六份 JSON 归一到统一底座，Issue↔评论按编号关联 | 97,034/115,280 可关联（损失 18,246） |
| 变换 | 建统一分类字典（入口—能力—环境—类型—结果）；TF-IDF 词+二元组 | 114 个不同标签、83,293 次标签出现 |
| 规约 | 只保留创建时可见字段进模型；Apriori 卡阈值降维 | 609 频繁项集 → 169 条规则 → 12 条核心 |

三条必须一直挂着的质量事实：

1. **评论关联损失 18,246 条**（15.8%）→ "无回复"比例可能被高估。
2. **论坛正文非随机覆盖 10.5%** → 主题份额不能外推。
3. **Issue 标签是维护者标注行为** → RQ2 算的是分流习惯，不是故障发生率。

### 2.4 最关键的口径：closed 不是 fixed

| 状态 | 数量 | 占全部 Issue | 能不能算"解决" |
|---|---:|---:|---|
| 仍开启（普通） | 16,547 | 59.6% | 不等于未修复 |
| 已重开（reopened） | 154 | 0.6% | 曾关闭后重开，不能并入普通 open |
| 标记完成 completed | 7,199 | 25.9% | 状态机"完成"，含"无法复现/已修复/不再需要" |
| 重复关闭 duplicate | 2,059 | 7.4% | 重复合并，不是解决 |
| 不计划处理 not_planned | 1,797 | 6.5% | 主动不处理 |

`closed` = 11,055 条（39.8%），是 completed + duplicate + not_planned 的**聚合状态**，不是一个与它们并列的互斥类别。

**任何"解决率"都必须说明：有没有把 duplicate 和 not_planned 也当成解决。** 第 5.5 节会把这句话变成一个具体数字：39.8% 里，30 天内真正完成的只有 18.7%。

## 3. 第二部分 · 方法（四个 RQ）

### RQ1 · 用户在讨论什么

**在做什么**：把 4,307 条无标注帖子自动分成 8 类。
**为什么这样做**：论坛没有内容分类（版块是用户自选的容器），要谈"用户关心什么"必须先有内容分类。
**方法**：
1. 仅取有正文主题，去模板页脚
2. TF-IDF（词 + 二元组）
3. NMF 分解，k=8，Frobenius 损失，seed=42
4. 主题名由高频词规则生成
5. **每主题取权重最高 6 帖回读，给主题名做体检**
6. 版块分类与主题分类**分开报告**
7. 敏感性：仅用 2026-07 后普查正文重跑 + bootstrap 重采样

**结果**（分母 4,307）：

| # | 主题 | 帖数 | 份额 | 高频词 | 主版块 |
|---|---|---:|---:|---|---|
| 5 | MCP / 网络 / 扩展宿主 | 1,070 | 24.8% | server, mcp, tool, error | Bug Reports 74.3% |
| 0 | IDE 界面 / 窗口 / 编辑器 | 777 | 18.0% | window, chat, editor, ide | Bug Reports 54.4% |
| 4 | 云端代理与仓库协作 | 654 | 15.2% | cloud, github, repo | Bug Reports 54.3% |
| 2 | 模型、子 Agent 与任务路由 | 619 | 14.4% | model, subagent, composer | Bug Reports 50.2% |
| 6 | 订阅套餐与用量额度 | 379 | 8.8% | usage, plan, limit | Help 37.7% |
| 3 | Bot / Computer Use / 设备 | 367 | 8.5% | bot, grok, computer | Bug Reports 68.9% |
| 1 | 社区活动与线下聚会 | 229 | 5.3% | luma, join, community | Asia 25.8% |
| 7 | API Key / 第三方模型接入（残余） | 212 | 4.9% | openai, api, key | Bug Reports 59.9% |

**能得出什么**：
- 前四类合计 **72.4%** → 用户摩擦集中在"连接、界面、云端协作、模型路由"，而不是"模型答得好不好"。
- 主题 1（社区活动 5.3%）是**独立类别，不是痛点**，产品反馈占比 87.5%。
- 主题 × 版块 Cramér's V = **0.38**（中等相关）→ 版块和主题是两件事，"发到哪个版块"不等于"在讲什么"。所以需要两套分类。

**不能得出什么**：
- 不能说"72% 用户最痛"。这是**帖子占比**，不是痛感强度、不是用户人数占比。
- 不代表 NMF 主题是互斥业务分类：48 条回读 46 条贴合，但有两个混入案例（CLI 加 PATH 被分到 MCP；Grok 限流被分到 API Key）。
- 46/48 是**命名诊断，不是分类准确率**；回读是 LLM 辅助结构化阅读，不是独立双盲标注。

**稳不稳**（三个数字）：
- Spearman ρ = **0.976**（全量 vs 仅普查子样本的主题排序）→ 排序稳
- 匈牙利匹配余弦中位 **0.998** → 主题身份稳
- Bootstrap 平均余弦 **0.889**，但**主题 7 只有 0.555（min 0.403）**→ 主题 7 只能当弱主题，不能单独支撑结论

**独立扩展（不可合并）**：另一套 2026-04~09 英文首帖 9,498 条，编辑器界面 22.8% / MCP 与终端 22.8% / 模型套餐 20.7%，三类合计约 66%，方向一致。但两套语料时间窗、语言、抽样、清洗都不同，**"方向一致"只能作为线索，不能写成一个比例验证了另一个比例**。且该扩展双人盲审未完成（A 0/140、B 0/140），只作探索性描述。

### RQ2 · 问题如何组合

**在做什么**：找出哪些标签经常一起出现。
**类比**：把一条 Issue 当成一次超市购物篮，标签是商品，Apriori 找"买了 A 的人多半也买 B"。
**三个指标缺一不可**：
- 只看支持度 → 挑出一堆高频废话（bug 占 80.3%，和谁搭配都"高"）
- 只看置信度 → 挑出小样本巧合
- **提升度 lift 是唯一能判断"是不是真关联"的**

**方法**：27,756 → 有标签 27,320 → 多标签事务 25,519；114 个标签、83,293 次出现。
阈值：支持度 ≥ 0.002、置信度 ≥ 0.3、提升度 ≥ 1.2、最小计数 50、最大项集 4、最大前件 2。
结果：**609 频繁项集 → 169 条规则 → 去重后 12 条核心规则**。

**结果（12 条中的代表作）**：

| ID | 规则 | 支持度 | 置信度 | 提升度 | 怎么读 |
|---|---|---:|---:|---:|---|
| R01 | windows-os → app | 19.9% | 71.5% | 1.38 | Windows 桌面是最大的问题容器 |
| R02 | app → windows-os | 19.9% | 38.3% | 1.38 | **反向置信度只有 38%**，方向不能反着写 |
| R10 | tui → cli | 4.1% | 49.8% | 2.19 | 提升度最高，但这是**标签层级**，不是因果 |
| R20 | computer-use → app | 2.9% | 95.4% | 1.84 | 置信度最高，但覆盖仅 3.0% |
| R29 | app; connectivity → bug | 2.6% | 96.9% | 1.21 | 桌面+连接几乎总以缺陷出现，可直接进网络排查 |

**能得出什么**：问题组合有清晰的**入口—能力**结构（Windows 桌面、CLI/TUI、浏览器/Computer Use、沙箱、远程云各自成组）。可用于：
- triage 路由（`app; connectivity` 直接给网络组）
- 回归测试组合（TUI+CLI、sandbox+Windows）
- 标签质检（打 TUI 应自动补 CLI）

**三种失真**（这一页是 RQ2 的价值所在）：
1. **不稳定**：12 条规则里只有 **2 条**在 ≥75% 可评估季度满足 lift ≥1.2；多数规则只有 2–3 个可评估季度，因为标签体系 2026 年才扩展。
2. **漏标**：48 条分层样本里，仅含 A 的 24 条中有 4 条应补 B → **漏标率代理 16.7%**（TUI 缺 CLI 2 条、桌面 Computer Use 缺 APP 2 条）。
3. **负关联也不是结论**：`app` × `cli` 的 lift 只有 **0.09**，`enhancement` × `windows-os` 0.23——看起来像"互斥"，实际是**标注时习惯只选一个入口**。

**不能得出什么**：规则不能写成"某入口导致某故障"。标签是维护者标注行为，规则捕捉的是标注习惯与使用路径的混合。

### RQ3 · 反馈如何处理

**在做什么**：描述一条 Issue 从创建到关闭的全过程，并尝试预测它会不会被快速处理。
**为什么不直接算平均天数**：到快照还没关的 Issue，排掉 → 等于假设它们明天就关（低估处理时长）；当 0 天 → 等于假设立刻关了（高估效率）。两种都错。所以用生存分析——它专门处理"还没结束"的数据。这是课外补的方法。

**三个时钟，不是一个 SLA**：

| 指标 | 分母 | 观测 | 比例 | 中位天数 | P90 |
|---|---:|---:|---:|---:|---:|
| 首次外部人类回复 | 27,756 | 15,417 | **55.5%** | 1.02 | 47.3 |
| 3 天内首次外部回复（固定窗） | 27,116 | 9,150 | 33.7% | 0.14 | — |
| 首次维护者回复 | 27,756 | 462 | **1.66%** | 0.71 | 67.9 |
| 已关闭 | 27,756 | 11,055 | **39.8%** | 2.01 | 87.2 |
| 30 天内关闭（固定窗） | 22,722 | 7,206 | 31.7% | — | — |
| 满 90 天仍开启 | 15,090 | 5,783 | 38.3% | — | — |

读法："社区很热、官方很冷、关闭很长"。
**1.66% 必须带分子分母（462/27,756）**，而且不能说"官方只处理 1.66%"——维护者身份是按 author_association 判定的，有合作者之外的人也在回。准确说法是"**维护者公开回复覆盖率 1.66%**"。

**长尾是真的**（Kaplan-Meier，全样本）：
- 中位关闭时间 **127.8 天**
- 30 / 90 / 180 天仍未关闭：**71.3% / 57.5% / 44.4%**
- 已关闭样本中位 **2.01 天** → **条件中位数与生存中位数必须同时报**，否则低估长尾

**分组差异（描述性，非随机分组）**：

| 入口 | n | 有外部回复 | 首回复中位 | 30 天关闭率 | 满 90 天仍开 |
|---|---:|---:|---:|---:|---:|
| cli | 7,050 | 66.4% | 0.39 | 42.0% | 26.4% |
| tui | 2,361 | 68.8% | 0.81 | 38.1% | 30.5% |
| app | 11,906 | 43.7% | 2.03 | 20.9% | **60.5%** |
| app-server | 1,891 | 52.7% | 2.37 | 16.6% | **69.4%** |
| ios | 270 | 32.2% | 5.28 | 13.2% | **69.3%** |

环境：linux 64.1% / 40.9% 明显优于 windows 50.9% / 26.5%。
远程：remote 30 天关闭 22.5% < non-remote 32.7%。

**最重要的修正 · 把 closed 拆成三种竞争结局**（Aalen–Johansen，N=27,585）：

| 指标 | 估计 | 说明 |
|---|---:|---|
| 30 天 completed 累积发生率 | **18.7%** | bootstrap 18.3–19.1 |
| 30 天 duplicate / not_planned | 6.5% / 3.6% | 合计约 10.1%，都不是"解决" |
| 30 天任意关闭 | 28.8% | 三种原因之和 |
| 90 天 completed | 27.5% | 长尾仍在累积 |
| 固定 30 天窗口：completed vs 任意关闭 | 20.8% vs 31.9% | **差 11.2 个百分点** |

**这一条会改结论**：如果说"解决了四成"，是把重复关闭和不处理也算进去了。拆开后，30 天真正完成的只有 18.7%（AJ）/ 20.8%（固定窗口）。方向不变，量级完全不同。

三方可复现：交付结果 / 交付脚本原样重跑 12/12 / 本项目独立实现 Aalen–Johansen 17/17 一致，曲线最大差 < 1e-15。reopened 两种处理对 30 天 completed 影响 0.11pp，截点变化影响 0.01pp —— **点估计几乎不动，但报告必须固定写清用哪个截点**。

**预测任务（结论：做不好，但这是有价值的结论）**：

| 任务 | 最佳模型 | AUC | AP | 训练→测试正例率 |
|---|---|---:|---:|---|
| 30 天内关闭 | text_logistic | 0.553 | 0.197 | 44.2% → 14.4% |
| 3 天内首次外部回复 | text_logistic | 0.605 | 0.256 | 40.8% → 19.0% |
| 90 天以上长期未关闭 | metadata_hgb | 0.555 | 0.732 | 23.4% → 70.2% |

- 已用时间切分 + purge gap；特征只含**创建时可见**字段（标题/正文、长度、有无代码、创建时间、作者身份），不含最终标签、入口/环境派生字段、状态、closed_at、评论。
- AUC 0.55–0.61，比随机好一点，离可用很远；阈值 0.5 召回 4%–48%，Top10% 召回也只有 11%–16%。
- 正例率漂移（44%→14%）说明"时间外"比交叉验证难得多；这是**分布漂移**，不是单纯模型不行。
- 残余泄漏风险无法消除：标题/正文来自快照，可能被事后编辑。
- **只能做候选排序 + 人工复核，不能自动关闭或自动忽略。**

### RQ4 · 两个渠道差在哪

**在做什么**：比较 Cursor 论坛与 Codex Issues 的问题类型结构。
**最大的坑**：拿论坛的"版块"去比 Issues 的"标签"，比的其实是两家平台的分类体系设计，不是用户。
**方法**：统一窗口 2026-01-01 ~ 快照（论坛 13,653 主题、Issues 23,843 条），**只用标题文本 + 同一套关键词规则**，两渠道同一输入同一字典。
**代价**：覆盖率有限（type 维度未识别率 72.6% / 69.0%），这个代价必须写在结论旁边。

**结果 · 问题类型**（分母含 unknown）：

| 类型 | 论坛 | Issues |
|---|---:|---:|
| 缺陷 bug | 18.1% | **22.8%** |
| 使用求助 help | **3.5%** | 0.5% |
| 功能需求 enhancement | 2.8% | 4.1% |
| 连接 connectivity | 2.5% | 2.2% |
| 性能 performance | 1.3% | 2.2% |
| 未识别 unknown | 72.6% | 69.0% |

方向清楚：**Issues 更像"报缺陷"，论坛更像"问怎么用"。**

**结果 · 入口（条件命中率，分母是各渠道已识别记录）**：

| 入口 | 论坛 | Issues |
|---|---:|---:|
| app | 15.8% | 66.6% |
| cli | 36.2% | 18.3% |
| extension | 29.4% | 15.0% |
| 识别覆盖率 | **12.4%** | **45.0%** |

覆盖率差 **3.6 倍**，所以入口构成**只作条件描述，不外推总体渠道偏好**。

**这里有一个我们改过的错**：最初规则把"cursor"这个词判成桌面 app 入口，结果论坛里提到产品名的帖子全被识别成 app，得出"论坛以桌面端为主"——这是错的。收窄规则后论坛 app 从 39.9% 降到 15.8%（`00_综合报告.md` 6.3 表值），但同时暴露出覆盖率只有 12.4%，所以最后改成"条件命中率 + 覆盖率"双报，并把"Issues CLI 占比更高"这个结论撤回。

**互动指标**（定义不同，只做参考）：有公开回复 40.1% vs 50.5%；零回复 59.9% vs 49.5%；明确完成/采纳 11.4%（采纳答案）vs 18.4%（completed）——**这两个定义不同，不能直接比**。

**不可比字段清单**：浏览量/点赞、采纳答案、closed/completed、正文长度（10.5% vs 全量）、零回复定义、标签体系——六项全部标注"不可直接比较"及原因。

## 5. 业务理解：这个项目最后真正说明了什么

抛开具体数字，三条结构性判断：

**第一，AI 编程工具的竞争点已经从"模型好不好"移到"接得上、看得懂、连得通"。**
主题占比重最高的四类（MCP/网络 24.8%、IDE 界面 18.0%、云端仓库 15.2%、模型路由 14.4%）里，只有最后一项沾模型本身。也就是说产品的主要摩擦发生在模型之外——扩展宿主、窗口行为、权限、仓库集成。这解释了为什么"换个更强的模型"不会让用户满意。

**第二，反馈运营的真实瓶颈不是回复速度，而是"回复的人不对"。**
55.5% 有外部回复、中位 1 天——社区响应其实不慢。但维护者公开回复覆盖只有 1.66%。所以问题不是"没人理"，而是"理的人不承担修复责任"。运营指标如果只看"首响时长"，会得到一个虚假的健康信号。

**第三，闭环口径错了，所有效率指标都会系统性乐观。**
39.8% 关闭里，30 天真正完成 18.7%。duplicate 与 not_planned 在 30 天已占 10.1%。这不是数据造假，是**状态机语义与业务语义不一致**——把状态机的"关闭"当业务的"解决"，KPI 就会自我美化。这条比前面两条更普适，换任何产品都成立。

## 6. 如果被追问

| 可能的追问 | 答法 |
|---|---|
| 为什么不做深度学习/大模型分类？ | 4,307 条无标注语料，NMF 可解释、可复现、主题名可回读验证。上 BERT 会得到更难解释的簇，且无法回答"份额"这个问题。 |
| 为什么 K=8？ | 重构比例随 K 增大单调改善，但 UMass、余弦轮廓、主题多样性不同时指向同一 K。K=8 是兼顾可读性与原报告连续性的工作设定，**不宣称唯一最优**（见 `outputs/rq1/09_k_selection.csv`）。 |
| 46/48 是不是准确率？ | 不是。是**主题命名与边界诊断**，样本按主题分层、LLM 辅助阅读、非双盲。正式提交前应抽 20% 人工复核。 |
| AUC 0.55 为什么还要报？ | 因为"公开元数据信号不足"本身就是结论——它说明要预测处理结果，必须接内部日志（状态变更、错误码、人力分配），而不是继续在文本上堆模型。 |
| 18.7% 和 20.8% 哪个对？ | 都对，口径不同：18.7% 是含删失的 Aalen–Johansen 累积发生率，20.8% 是固定 30 天窗口的简单比例。**报的时候必须说明用哪个。** |
| 数据会不会过时？ | 会。快照是 2026-09-13。但"先问分母、再问方法边界、最后说结论"这套流程不过时。 |
| 最大的先天限制是什么？ | 所有时间都来自快照反推，看不到真实的状态变更事件流。接入内部日志是唯一根治办法。 |
